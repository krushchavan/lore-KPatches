🔥 TODAY [RFC PATCH 0/1] mm/swap: keep reclaim batches contiguous on swap
Show 1 individual patches
  • [1/1] mm/swap: allocate contiguous swap slots for a reclaim batch
Needs Work LLM (per-reviewer) RFC

This patch aims to reduce the number of I/O requests on a swap device by keeping reclaim batches contiguous. The current implementation of swap allocation and deallocation can lead to scattered writes, resulting in increased I/O requests. The patch modifies the allocator to allocate contiguous free slots for a reclaim batch, reducing the number of small requests and improving throughput. This is achieved by informing the allocator about the size of the batch and allowing it to allocate contiguous slots accordingly. The goal is to reduce the overhead of swap I/O operations and improve system performance.

This patch series improves the performance of Btrfs's allocator by reducing unnecessary operations on block groups, particularly in large and mostly full file systems. The changes include skipping unhelpful size class relaxing allocation loops, removing redundant checks, and optimizing the find_free_extent function to skip locked block groups and size classes. These improvements result in significant speedups for certain workloads, such as running 20k fallocates on a sparse file system, which was previously taking around 40 seconds but is now completed in about 7 seconds.

[PATCH v2 7/7] btrfs: remove block_group data_rwsem and delalloc_bytes Neutral llm-chunked-no-replies Awaiting Review

This patch removes the `data_rwsem` and `delalloc_bytes` fields from the Btrfs block group data structure, as they are no longer needed after the removal of the v1 space cache in a previous commit. The `data_rwsem` was only used by the v1 space cache write path, which has been removed, and `delalloc_bytes` is now only printed but not used. Removing these fields simplifies the code and eliminates confusing indirection machinery dedicated to separating delalloc calls from non-delalloc calls.

Ongoing Submitted 2026-10-19 🔥 TODAY [PATCH] mm/page_alloc: let the highest memory node recover from hopeless state Needs Work LLM (per-reviewer) Under Review

This patch fixes a problem where the highest memory node in a system cannot recover from a 'hopeless' state, even when its zone recovers above the high watermark. The issue arises because the current code checks if there is another memory node available for allocations to fall back to by looking at the next higher-numbered node ID, which always returns false for the highest node. This patch changes the check to count the number of nodes with a state of N_MEMORY, effectively checking if any other node exists. As a result, the highest node can now recover from its hopeless state and kswapd will be re-enabled.

🔥 TODAY [PATCH v1] mm: move LRU size stat updates out of lru_lock in folio batches Needs Work LLM (per-reviewer) Under Review

This patch moves the updates to LRU size statistics out of the lru_lock critical section in folio batches, reducing contention and improving performance. The stats are accumulated while holding the lock and applied after dropping it, resulting in at most one update per LRU list per batch. This change is expected to improve throughput by reducing the time spent waiting for the lru_lock and making the code more efficient.
