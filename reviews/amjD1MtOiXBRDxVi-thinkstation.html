Submitted: 2026-07-28
Active on: 2026-07-28
Patch summary
This patch separates out the logic for CONFIG_PERSISTENT_HUGE_ZERO_FOLIO in the mm/huge_memory code, potentially moving huge_zero_folio to BSS when this configuration is enabled. The original code had issues with NULL pointer dereferences and unexpected reordering of function calls.
Lorenzo (ARM) 2026-07-28 Reviewed-by Needs Work LLM
Reviewer Lorenzo noted that mm_get_huge_zero_folio() will return NULL without attempting to allocate again, and suggested moving huge_zero_folio to BSS for CONFIG_PERSISTENT_HUGE_ZERO_FOLIO=y to prevent this issue. Additionally, he pointed out that the current behavior is existing and should be preserved in the backport. Reviewer questioned whether returning NULL from mm_get_huge_zero_folio() is sufficient to handle allocation failures, and suggested moving huge_zero_folio to BSS for CONFIG_PERSISTENT_HUGE_ZERO_FOLIO=y to guarantee its availability. Reviewer noted that subsys_initcall() discards errors, potentially leading to an oops on a small allocation failure in mm_get_huge_zero_folio(), and suggested addressing this issue in a follow-up patch. Reviewer questioned the necessity of reordering huge_zero_init() calls, suggesting that it doesn't make a difference and offering to reorder if a respin is needed
