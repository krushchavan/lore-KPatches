[PATCH 0/3] block: skip the blkcg walk in blk_cgroup_congested() when nothing is throttled

Patch summary
This patch set optimizes the blk_cgroup_congested() function by skipping unnecessary walks of the block cgroup (blkcg) hierarchy when no tasks are being throttled. The current implementation incurs a significant performance cost due to frequent cache line loads and RCU read-side pairs, especially in systems with deep container hierarchies. To address this, the patch introduces a global gate that only performs the walk when there is at least one blkcg with a non-zero congestion count. Additionally, two patches fix issues that can leave a blkcg permanently marked congested, which would otherwise cause unnecessary throttling of tasks in affected cgroups.
Usama Arif (author) 2026-08-10 Neutral LLM
Author responded to a concern about blkcg_clear_delay() overwriting state managed by other policies, explaining that the issue is specific to cases where multiple block cgroup policies coexist on the same device and one policy's data is freed while the other remains active. The author suggests that this scenario might not be common enough to warrant addressing.

[Severity: High]
Does this unconditional call to blkcg_clear_delay() overwrite state managed
by other policies?

Since use_delay is shared among block cgroup policies, if iocost never
actually applied a delay, this might forcefully zero out the delay state
managed by other active policies like blk-iolatency. 

Would it be safer to check if iocost had actually set a delay before clearing
it here?
---


My understanding is that this requires both policies to coexist on the same
device/blkg?

I believe the main problematic sequence would be:

  1. io.latency owns positive use_delay.
  2. io.cost policy data exists but may never have delayed anything.
  3. io.cost policy data is freed while the blkg survives.
  4. Its unconditional clear removes io.latency\u2019s state.

With only one policy, the terminal clear is correct and clearing zero is harmless.

The concern is narrower still: ordinary disk/cgroup destruction removes the whole
blkg, so the main observable case is one-policy activation rollback or deactivation
while the other remains active.

I am not sure if this is something that is done by users? So might not need
to be addressed?

Thanks,
