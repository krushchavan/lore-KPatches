[PATCH v1 0/3] mm: read root memcg stats from global counters instead of flushing

Patch summary
This patch series addresses the issue of memcg stats flushing, which can be costly and introduce staleness in statistics. For the root memcg, it's possible to directly read global counters instead of going through rstat, as they are always up-to-date. The patches modify various call sites to use node counters for reading LRU sizes, working set, rotation, and reclaim writeback counts. This approach reduces the number of flushes required, especially for the root memcg, which can be a performance bottleneck. The changes also improve the accuracy of statistics by reducing staleness. The series consists of three patches: one fixes the zswap shrinker's count for the root memcg, another adds a function to read node counters for the root memcg, and the third modifies DAMON's quota goals to use node counters instead of flushing.

functions I was looking at were account_slab() and

criteria are met (eg the cache had SLAB_ACCOUNT set or the allocation
had the __GFP_ACCOUNT gfp flag set and the allocation was not from a
root memcg).

Author Joanne Koong addressed a concern about kernel memory accounting for allocations made by tasks running in the root cgroup, explaining that it was intentionally designed to avoid extra overhead costs and proposing an alternative approach of reading node counters instead of going through rstat. Author agrees that the feedback is reasonable and asks for input from other memcg developers.
Show original comment 
I think there's 2 categories:
a) the allocation isn't acccounted to any memcg (eg kernel page
tables, hugetlb when hugetlb accounting is off, unaccounted slab
caches and kmallocs w/out __GFP_ACCOUNT, and most vmalloc). These
values only get added to the node counter

b) the allocation is accounted, but it comes from a task running in
the root cgroup (eg kernel stacks, user + secondary page tables,
accounted slab, etc)

I think a) has to stay as is since it's not linked to any memcg. For
b), it seems intentional from the original commit that added kernel
memory accounting logic (commit 7ae1e1d0f8ac ("memcg: kmem controller
infrastructure")). The commit message for that explicitly says
tracking kernel memory pages to a given memcg "will happen whenever
the caller includes the flag __GFP_KMEMCG flag and the task belongs to
a memcg other than the root". (__GFP_KMEMCG later became
__GFP_ACCOUNT). I wonder though if this was to avoid extra overhead
costs (eg for systems that don't use cgroups) on the hot paths, since
it would need to do non-trivial per-object work. If root read the node
counters for the stats that are in category b (excluding the stats
that are in both category a and b) instead of going through rstat
(which is what this series does for the LRU stats), there wouldn't
need to be any extra overhead at allocation time, since nothing would
need to be tracked.

---

That seems reasonable to me. memcg folks, do you have any thoughts on this?

Thanks,
Joanne
