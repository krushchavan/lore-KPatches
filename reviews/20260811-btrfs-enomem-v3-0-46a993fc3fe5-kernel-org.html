[PATCH v3 0/6] btrfs: handle -ENOMEM errors in some synchronous dirops without aborting

Patch summary
This patchset addresses a long-standing issue in the Btrfs file system where memory allocation failures can cause an abort during synchronous directory operations. The patches rework the code to perform allocations upfront, before reaching the point of potential aborts. This approach is designed to work in conjunction with another series that aims to prevent new memory allocations from triggering ENOMEM errors. Although this patchset does not cover all possible cases where ENOMEM can occur, it provides a significant improvement over the current state and is intended as an intermediate step towards fully addressing the issue.

David Sterba 2026-08-20 Reviewed-by Needs Work LLM
Reviewer David Sterba expressed concern about excessive stack usage in the patch, citing a potential trade-off between allocation failure and stack consumption. He suggested arguing for the chosen stack size in the changelog and exploring alternative memory allocation strategies such as using __GFP_HIGH.
Show original comment 
112 is too much for on-stack, we've avoided that for btrfs_path in
particular, except some justified cases. This means in general the
beginning of call stack like ioctl, syscall handler and such. Otherwise
we assume there are other layers in the IO stack, like block device
drivers (DM), NFS, encoding layers or networking (iscsi), and obviously
the lowest level device drivers.

The trade off with possible allocation failure vs stack consumption
needs to be argued in the changelog, "is just 112" is not sufficient.

Getting back the consumed stack space is painful, we've been reducing
unneeded or redundant parameters of functions for years. The gains are
like -8 bytes here and -8 bytes there, allocation of +112 wipes that out.

If the place of allocation is critical we can consider that but we have
too many of them, anywhere during the transaction commit path or
irreversible metadata changes. Possibly using __GFP_HIGH could work, but
I haven't explored that.

Qu added the patches to for-next but I had no chance to look closely at
this patchset yet and am hesitant to leave it like that.

  btrfs_orphan_add aborts by errno:                                   
                                                                                                                  
  ┌────────────┬────────┬───────┐                                     
  │   errno    │ events │ hosts │                                     
  ├────────────┼────────┼───────┤                                     
  │ -5 EIO     │ 131    │ 127   │                                     
  ├────────────┼────────┼───────┤                                     
  │ -28 ENOSPC │ 1      │ 1     │

  └────────────┴────────┴───────┘                                     
  Same result with the cascade filter dropped (293 events / 270 hosts, all -5).                                   
                                                                                                                  
  Three controls make that a real negative rather than a query artifact:                           

  1. ENOMEM aborts exist — 475 events / 471 hosts in the same window, so the query would find them.
  2. The signature is detectable and the code is live — the identical abort site in btrfs_orphan_add: fires for 270 hosts with -5. And btrfs_orphan_add() passes ret straight to btrfs_abort_transaction() with no remapping, so a -12 would print as -12.                     
  3. The path is hot — in the base tree btrfs_orphan_add() is called from btrfs_unlink() (nlink→0), btrfs_rmdir(), btrfs_create_new_inode() (O_TMPFILE), and btrfs_rename() (victim nlink→0). That allocation runs on essentially every file deletion fleet-wide.                 

Where the ENOMEM aborts actually are (hosts/30d): btrfs_rename 147, convert_free_space_to_extents 116, btrfs_add_link 67, convert_free_space_to_bitmaps 56, btrfs_replace_file_extents 42, btrfs_create_new_inode 16.
