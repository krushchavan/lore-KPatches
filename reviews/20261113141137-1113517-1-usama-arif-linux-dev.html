[PATCH v3 2/2] x86/lib: Use REP MOVSB for large memcpy() on ERMS CPUs without FSRM

View on lore.kernel.org →
Submitted: 2026-11-13
Active on: 2026-11-13
Patch summary
This patch modifies the x86 memcpy function to use REP MOVSB for large memory copies on ERMS CPUs without FSRM support. The patch introduces a new helper function, memcpy_erms, which uses REP MOVSB when the copy size is greater than or equal to 2048 bytes. This approach aims to improve performance by taking advantage of the optimized instruction set available on ERMS CPUs. The patch also includes alternative implementations for different CPU features and provides a fallback to the original memcpy implementation when necessary.

The problem with this approach two-fold:

 - many memcpy() calls aren't actually memcpy() calls on a C level

 - many memcpy() that *are* calls on a C level should never be calls
in the generated code

That first case is for things like structure copies etc. And it's
common, and it's important, although for the kernel it's usually a
non-issue because it's *typicay* a small constant-sized copy, which
brings us to the second case...

The second case is hugely important. The compiler needs to turn small
memcpy() calls into just loads and stores. Calling "memcpy()" for a
known 64-byte copy is hugely inefficient.

We used to - long ago - do that "constant small sizes" thing by hand.
It was a huge pain. We now rely on the compiler to do it.

End result: we must *not* hide 'memcpy()' from the compiler for
performance reasons, and we cannot catch all cases anyway because the
compiler generates implicit memcpy calls.

This is why I really wish we had the compiler just generate a
different sequence for 'call memcpy'. One that used a different
callign convention - preferably just the 'rep movs' one so that we
could just rewrite the call with 'rep movsb' in place.

Without compiler support, we're kind of screwed.

Reviewer David Laight pointed out that the alternative code path for ERMS CPUs without FSRM should use a cmp immediate of 32 bytes instead of 2048, as changing it from 2048 to 32 made aligned warmed copies 16.5% slower. Reviewer suggested that instead of using REP MOVSB for large memcpy() on ERMS CPUs without FSRM, the patch could detect small constant sizes and call the real memcpy() function, which would allow the compiler to inline them as a series of moves. Reviewer David Laight expressed concern that the use of REP MOVSB in memcpy_erms function may not be optimal due to its non-standard calling convention, which could lead to issues on certain architectures.
