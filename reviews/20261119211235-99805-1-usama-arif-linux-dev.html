Patch summary
This patch series fixes two bugs in the Linux kernel's perf/core module related to software event sample data. The first bug, present since v6.3, occurs when a sampling event inherits an uninitialized sample ID and timestamp from a previous event, causing issues with concurrent 'perf record' sessions. The second bug, introduced in v6.1, allows BPF programs to read uninitialized stack contents through the bpf_perf_event_data::addr field. The patches initialize the struct for each matching event, prevent BPF programs from reading uninitialized data, and stop zero-initializing the struct in do_perf_sw_event(). These changes improve performance by reducing the time it takes to handle context switches.

    perf/x86/amd/ibs: Don't leak stack contents through PERF_SAMPLE_WEIGHT_STRUCT

    For a load that missed the data cache, perf_ibs_parse_ld_st_data()
    reports the miss latency as the sample weight and marks
    PERF_SAMPLE_WEIGHT_TYPE as done, so perf_prepare_sample() leaves the
    field alone. With PERF_SAMPLE_WEIGHT_STRUCT it writes only var1_dw and
    var2_w, but perf_output_sample() copies all 8 bytes of the union into

perf/core: Fix perf_sample_data reuse across software events

do_perf_sw_event() passes one on-stack struct perf_sample_data to every
matching event. perf_prepare_sample() fills in the fields an event
samples, marks them in data->sample_flags and skips fields that are
already marked, and those marks survive from one event to the next.

So a sampling event later in the list emits the sample ID, timestamp,
pid/tid and callchain prepared for an earlier one. Its record size is
computed from the earlier event's dynamic fields as well and can come
out smaller than what is written, in which case the kernel writes past
its ring-buffer reservation over the records that follow.

Two "perf record -e page-faults,context-switches -c 1 -a" sessions
running at the same time hit this: the one started first gets the
other's sample IDs and fails with "Bad address".

Commit:

   1d1bfe30dad5 ("perf/core: Fix perf_sample_data not properly initialized for different swevents in perf_tp_event()")

fixed the same problem for tracepoints. Do the same here: initialize
the struct for each matching event. While at it, drop the unused 'data'
argument of perf_swevent_match().

perf/core: Don't let BPF programs read an uninitialized sample address

A BPF program attached to a perf event gets a struct
bpf_perf_event_data, and reading its addr field turns into a load from
the perf_sample_data the sample is being assembled in. The verifier
allows that load no matter which fields the event samples.

perf_sample_data_init() used to store the address unconditionally, so
the program read 0 when there was none. To touch fewer cachelines, it
now stores the address only when it is non-zero, and
perf_prepare_sample() fills it in only when the event samples it
(PERF_SAMPLE_ADDR, PHYS_ADDR or DATA_PAGE_SIZE). For all other events,
including context switches, cpu-clock and hardware counters like
cycles, the program reads whatever was left in that stack slot, often a
kernel pointer.

Kernels built with CONFIG_INIT_STACK_ALL_ZERO, the default when the
compiler supports it, mostly hide this by clearing the struct on
function entry. With INIT_STACK_ALL_PATTERN the program reads the fill
pattern instead.

Clear the address before running the program if nobody filled it in,
the same way the SIGTRAP path already checks PERF_SAMPLE_ADDR before
using it. Events without a BPF program are not affected.
