[PATCH 2/2] x86/kstack_erase: Use REP STOSQ for large stack fills

View on lore.kernel.org →
Submitted: 2026-11-21
Active on: 2026-11-21
Patch summary
This patch modifies the x86 kernel's stack erasure function to use REP STOSQ for large stack fills, which is a more efficient instruction than a plain loop. The change was motivated by benchmarking results that showed significant performance improvements (up to 23% reduction in execution time) compared to the original implementation. The patch also includes some discussion about different variants of the erasure function and their relative performance characteristics.
David Laight 2026-11-21 Inline Review Reviewed-by Needs Work LLM
Reviewer David Laight noted that the patch's performance results are not conclusive, as they only show a significant improvement for large stack fills and do not account for other factors such as branch prediction, cache behavior, and instruction-level parallelism. The reviewer, David Laight, notes that the lfence instruction takes long enough to overlap with setup times for REP STOSQ, making it difficult to measure meaningful timings for short operations. He also mentions that the TSC (Time Stamp Counter) doesn't measure clocks accurately and that CPU speed changes during long-running benchmarks. Additionally, he provides benchmark results using PERF_COUNT_CPU_CYCLES counter and direct execution of rdpmc instructions, showing that REP STOSQ is slower than REP MOVSB for large stack fills.

I've updated my benchmark code and run some tests on zen5.
This uses the PERF_COUNT_CPU_CYCLES counter but directly executing rdpmc.
I then use data dependencies from the original count to the test code,
and from the test result to the second rdpmc (which nicely has a register
number) to get a time that includes the test function with little overhead.
The clock count for an empty test function is 25, 32 with a memory read.

Each test is run 10 times and the clock count for each shown separately.
The first column includes the cost of the I-cache loads and any branches
that get mispredicted because (in these cases) the length changes.
This is most obvious for the libc calls.

I added enough barrier() and OPTIMIZER_HIDE_VAR() to get the 'longs'
loop to be sane - it sets/copies two 64bit locations each iteration.
Both tests manage a loop iteration every clock (on zen5).

The cutoff for 'rep stos' is pretty much 1k.
For memcpy() it is a bit lower.

'rep movsq' is slightly slower than 'rep movsb' because of the 'len /= 8'.
But it is much slower for counts of 1 (included above) and 0.
