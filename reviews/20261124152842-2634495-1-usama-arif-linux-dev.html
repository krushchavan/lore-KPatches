[PATCH] KVM: arm64: Reduce the stage-2 page cache on 64 KiB hosts

View on lore.kernel.org →
Submitted: 2026-11-25  ·  Last comment: 2026-11-27
Active on: 2026-11-27 • 2026-11-26 • 2026-11-25
Patch summary
This patch reduces the size of the stage-2 page cache in KVM for arm64 hosts with 64 KiB pages, from 40 to 8 entries. This change is motivated by the observation that most of the cached pages are never used and the actual memory requirements are much lower than previously assumed. The new value still covers the minimum required for a stage-2 fault and leaves room for additional table allocations. The patch affects only arm64 hosts with 64 KiB pages, leaving other configurations unchanged.
Leonardo Bras 2026-11-25 Neutral LLM
Reviewer Leonardo Bras asked if the issue of high memory usage by vCPU page caches on 64 KiB hosts had been reproduced in newer kernel versions, specifically v7.4-rc1 or later, and suggested that a change introduced by Lorenzo Stoakes might improve the situation.

On Tue, Nov 24, 2026 at 07:28:42AM -0800, Usama Arif wrote:
> When a stage-2 fault may need new page tables, KVM first tops up the
> vCPU's page cache: if it holds fewer pages than the fault might need, it
> is refilled to KVM_ARCH_NR_OBJS_PER_MEMORY_CACHE, which arm64 sets to
> 40. Unused pages stay in the cache until the vCPU is destroyed.
> 
> With 64 KiB pages, that is 2.5 MiB per vCPU, and most of it is never
> used. Stage-2 has at most three levels and the root is preallocated, so
> a fault needs at most two new table pages (kvm_mmu_cache_min_pages()).
> As every last-level table covers 512 MiB, an 8 GiB guest needs just 17
> table pages to map all of its memory, while its four vCPU caches get
> filled with 160.
> 
> On a production host with 64 KiB pages running 101 VMs with four vCPUs
> each, the caches were still 86% full. The memory used:
> 
>                         before      after
>   per-vCPU capacity     2.5 MB     512 KB
>   all 404 vCPUs         869 MB     <= 202 MB
> 
> Let's lower the capacity to 8 with 64 KiB pages, In the production
> usecase above, it frees at least 667 MB. That still covers the two-page
> minimum and leaves room for several table allocations per refill. 4 KB
> and 16 KB pages keep 40.
> 
> The temporary cache in kvm_phys_addr_ioremap() uses the same capacity,
> but it is topped up before every page it maps, so 8 is sufficient there
> as well. The pKVM hypervisor memcache and the eager split cache don't
> use this capacity.

avoid the waste altogether.

Hi Wei-Lin,

IIUC, every time we topup, we call a mmu_memory_cache_alloc_obj() for every 
one of the objects in the array. So as it is today it runs it 40 times, and 
waits until it runs down to allocate up to 40 again.

With the change, it will run 4, then up to 4 how many times are needed.

So having a smaller cache can potentially save both cputime and memory if 
the cache is not that oftenly used. That being said, allocating 40 in 
sequence would be faster than 4 * 10 because the instruction / data cache 
is hot.

I think the only way to evaluate the performance impact is by running some 
benchmarks.

When a stage-2 fault may need new page tables, KVM first tops up the
vCPU's memcache: if it holds fewer pages than the fault might need, it
is refilled to KVM_ARCH_NR_OBJS_PER_MEMORY_CACHE, which arm64 sets to
40. Pages never return to the cache, and unused ones stay there until
the vCPU is destroyed.

The cache only has to cover a single map: every fault that can allocate
tables tops it up first, and a map allocates at most one table per
level below the preallocated root (kvm_mmu_cache_min_pages()). That is
at most three pages with 4 KiB and 16 KiB pages, and two with 64 KiB
pages.

With 64 KiB pages, the 40-page cache is 2.5 MiB per vCPU. As every
last-level table covers 512 MiB, an 8 GiB guest needs just 17 table
pages to map all of its memory, while its four vCPU caches get filled
with 160. On a production host with 64 KiB pages running 101 VMs with
four vCPUs each, the caches were still 86% full. The memory used:

                        before      after
  per-vCPU capacity     2.5 MiB     256 KiB
  all 404 vCPUs         869 MiB     <= 101 MiB

Let's size the cache to KVM_PGTABLE_LAST_LEVEL - KVM_PGTABLE_FIRST_LEVEL,
which is 4 pages and covers the deepest walk with one page to spare. On
the host above, it frees at least 768 MiB. Refills get more frequent,
but no more than four pages per vCPU ever sit unused. With 4 KiB pages,
the cache shrinks from 160 KiB to 16 KiB per vCPU.

Move the two level definitions to asm/kvm_types.h, so that the generic
top-up code in kvm_main.c can see them. kvm_pgtable.h still gets them
through linux/kvm_types.h.

The temporary cache in kvm_phys_addr_ioremap() uses the same capacity,
but it is topped up before every page it maps. The pKVM hypervisor
memcache and the eager split cache don't use this capacity.

When I mention cache locality above, I mean the cpu cache. Running the same

The question is would going from 40 to 3 slow things down?

At 40 you do 40 __get_free_page() calls on topup for the _first_ fault that hits
it, which adds latency to a random s2 fault (not great).

page table is next needed).

you go again...

With 3 in the cache you allocate up to 3 for each fault.

So in both cases you allocate the same amount of pages but in the 40 case it's
all bunched up on one s2 fault with a jump in latency, in the 3 case it's spread
out.

I'd say 3 is therefore the better choice.

Also, as mentioned elsewhere, you end up leaking pages once the S2 page tables
are setup until the vCPU is destroyed, as nothing clears down the cache
AFAICT. With 40 that's way more than with 3.

Subject: [PATCH] KVM: arm64: Size the stage-2 memcache from
 kvm_mmu_cache_min_pages()

When fewer than kvm_mmu_cache_min_pages() pages are left, a stage-2
fault that may need new tables refills the vCPU's memcache to
KVM_ARCH_NR_OBJS_PER_MEMORY_CACHE, 40 on arm64. A map allocates at most
one table per level below the preallocated root, which is
kvm_mmu_cache_min_pages() and at most 3 pages. Only vCPU destruction
frees the memcache, so whatever a refill leaves unused stays allocated:
up to 2.5 MiB per vCPU with 64 KiB pages. On a 64 KiB host running 101
VMs with 4 vCPUs and 1 GiB each, the memcaches held 986 MiB, against
25 MiB of stage-2 tables in use.

Size the memcache at twice the largest kvm_mmu_cache_min_pages() of the
VM's stage-2s instead, so that each refill covers at least two
worst-case maps. With NV, the vCPU's memcache also feeds the shadow
stage-2s, and a memcache's capacity can't change once used, so record
the largest value as each stage-2 is initialised. The VM's stage-2 is
set up at VM creation and the first shadow stage-2s by the first
KVM_ARM_VCPU_INIT, before any vCPU can fault, and later shadow stage-2s
have the same size. kvm_phys_addr_ioremap()'s temporary memcache uses
the same capacity, so arm64 no longer uses the value of
KVM_ARCH_NR_OBJS_PER_MEMORY_CACHE.

With a 48-bit IPA, the capacity is 4 pages with 16 KiB and 64 KiB pages
and 6 with 4 KiB pages; with the default 40-bit IPA, 2 and 4. On the
host above and on a production host also running 101 VMs with 4 vCPUs
each, both with 64 KiB pages and 48-bit IPA VMs:

                     memcaches                saved
                     before      after
  host above         986 MiB     81 MiB       905 MiB
  production host    869 MiB     <= 101 MiB   >= 768 MiB

A memcache now refills at most once every two tables, as a capacity of
4 does with 4 KiB pages and a 48-bit IPA. Measured that way, per fault
for the median vCPU, one VM at a time:

                                        40           4
  2M blocks split under dirty logging   4.9-5.1 us   4.9-5.0 us
  1G block split, then refaulted        2.7-2.8 us   2.8 us
  every fault allocating a table        4.0-4.1 us   3.7-4.1 us
