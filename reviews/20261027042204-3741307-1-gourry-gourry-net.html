[PATCH 0/6] mm: fix pfn walker races with memory offline

View on lore.kernel.org →
Submitted: 2026-10-27  ·  Last comment: 2026-11-03
Active on: 2026-11-03 • 2026-10-27
Patch summary
This patch series addresses six races in the Linux kernel's memory management code that can cause crashes or incorrect behavior when memory is offline. The patches introduce a new function, pfn_walk, which waits for pending page walkers before poisoning the memory map, and modify various functions to use this new function or hold get_online_mems() instead. This ensures that memory is not accessed after it has been marked as offline, preventing crashes and incorrect behavior. The changes are tested on a QEMU guest with three NUMA nodes and a pc-dimm left offline at boot, and the results show that the patches fix all six races without introducing any significant performance cost.
David (Arm) 2026-10-27 Reviewed-by Needs Work LLM
Reviewer David from Arm expressed concerns that the patch series is low priority and should be discussed further, citing a lack of real-world reports and suggesting that the issues are not as likely to happen as thought. He also suggested using an RCU for pfn_to_online_page() + zone->contig thingies instead of get_online_mems(), and proposed adding infrastructure in a separate patch rather than manging it into a patch that fixes a DEBUG_VM splat.

+ * Nothing keeps a section online once pfn_to_online_page() has returned. A pfn
+ * walker that holds no reference to the page does the check and looks at the
+ * memmap under this guard: remove_pfn_range_from_zone() waits for it before the
+ * memmap is poisoned and can be freed. That wait cannot be interrupted, and
+ * whatever a walker sleeps on under the guard, memory offlining waits for as
+ * well: leave the guard before copying to user space. mem_hotplug_lock is held
+ * during the wait: never take it under the guard.
+ */
+extern struct srcu_struct memmap_srcu;
+#define memmap_walk_guard()    guard(srcu)(&memmap_srcu)

I actually have a reason for these fixes other than "bot said bad".

We leverage ballooning and hotplugging as VM memory overcommit tools
and are finding that some of these race conditions crash them with
large MTBF.

While most of these are insanely narrow, they are not as unlikely to
happen as you think. A vCPU can take a vmexit in these windows much
more easily than a host can take an NMI or other interrupt.

Thankfully none of these (or the other series) appear to be obvious
security issues, but they are stability issues.

I have a reproducer for every single one of these (and the other
series) - but a handful are unreachable due to a 2-statement read
being emitted as a single read by the compiler (which can be undone
by a targeted compiler flag). Those were included for completeness.

--

On properly - I have a follow up series that fixes the zonelist walks
structurally, but it uses SRCU-fast on the fast path. The catch is that
PowerPC (and i think others?) don't SRCU-fast without atomics, so they
take a performance hit.  (It also doesn't help us for backports)

I've been weighing that solution over never freeing and/or prepopulating
zones - but this also results in performance impacts (leaving dead zones
in the list forces the allocator to walk them for no value).

Actual balloon inflation/deflation.  It is disgusting, but it's
effective.  Right now we use hotplug at boot to minimize the size of
cold machines to avoid thundering herd issues, and then add it when
they actually get allocated for work.

At runtime we use ballooning to reduce a VM to its actual RSS based
on PSI feedback (see: that virtio stats extension i sent you some while
ago), but would like to use hotplug to give the host a defense against
a storm of deflate_on_oom scenarios across a large number of guests.

Basically using PSI stats we can make guests do somewhat aggressive
proactive reclaim on without having to build any new tooling, and
while being able to back-off aggressively.

Free-page reporting is also on by default, but this only helps you if
your guests are being extra nice about things.

(spoiler: they're not! they're greedly little imps! :D)

My experiments made balloon prefer to try to reclaim movable regions
in contiguous blocks, and then just hand that contiguous block off to
virtio-mem for offline without having to drop the balloon.

tl;dr: This seems effective and works quite well.

Yes - but specifically this affects PowerPC because it:

 - does NOT have NMI-safe per-CPU operations
 - supports memory hotplug
 - uses atomics for SRCU-fast
