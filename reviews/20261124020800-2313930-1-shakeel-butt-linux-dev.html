Patch summary
This patch adds a warning when the maximum number of memory cgroup IDs is reached, preventing new cgroups from being created due to lack of available IDs. This issue was previously hard to detect as it only resulted in an -EBUSY error during mkdir operations without any logged warnings. The patch introduces rate-limited warnings to alert administrators when all IDs are in use.
Andrew Morton 2026-11-23 Reviewed-by Needs Work LLM
Andrew Morton noted that the patch does not handle the case where the ID allocation fails due to a lack of memory, and requested that the code be modified to check for this condition before printing the warning.

From: Shakeel Butt <shakeel.butt@linux.dev>
Subject: memcg: warn when memory cgroup IDs run out
Date: Mon, 23 Nov 2026 18:08:00 -0800

Every memory cgroup gets a 16-bit private ID, so a host can have at most
65,535 of them at a time, counting dead ones.  A dead memcg keeps its ID
as long as any swap slot still records it.  On Meta hosts that create many
short-lived cgroups, dead cgroups held this way filled the whole ID space.
After that, every mkdir of a cgroup with the memory controller failed
with -EBUSY: systemd could not start units, and container setup failed.

This was hard to see:

- Nothing is logged when the ID allocation fails. The only sign is
  -EBUSY from mkdir.
- Since commit 8290f45995f5 ("memcg: move memcg private ID refcount to
  objcg"), a dead memcg is freed even while swap still holds its ID. So
  nr_dying_subsys_memory in cgroup.stat can be 0 while the IDs run out.

Print a rate limited warning when the ID allocation fails because all IDs
are in use.

Shakeel Butt (author) 2026-11-24 Neutral LLM
Author acknowledged that the returned error from mkdir operation may not always indicate that memory cgroup IDs are out, and explained that they initially considered adding a vmstat but chose to implement a rate-limited warning instead.
Show original comment 
There are multiple software layers (binaries and libraries) between mkdir
operation and the folks debugging the failures. Not all software creating
cgroups log the returned errors. Also I am not sure EBUSY can only be when
we are out of memcg IDs. These errors can be transient as well. Initially I was
thinking of adding a vmstat but decided to go with a warning first.
