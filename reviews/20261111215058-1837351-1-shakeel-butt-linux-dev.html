Patch summary
This patch addresses long stalls in kernfs due to holding the kernfs_rwsem lock while allocating inodes and dentries. It achieves this by allocating inodes before taking the lock, using kernfs_get_inode_locked(), and only holding the lock around inode lookups. This approach reduces contention on the lock and prevents stalls caused by memory reclaim. The patch also fixes a related issue with kernfs_get_parent_dentry() by holding the lock only during inode lookup. Testing shows significant reductions in wait times for various tasks.

Yes, it builds on vfs-7.5.directory (base-commit ecdfc51a6a78).
Christian's fixup there dropped @lookup, so kernfs_get_inode_locked()
now takes just (inode, kn).

I don't think this patch needs @lookup.  inode_insert5() already
returns an inode that is already hashed, so an ilookup() first only
changes things for an inactive node.  Lookup and the fh_to_* paths
only get there with an active node, under the same kernfs_rwsem hold,
and fill_super works on a new superblock.  In ->get_parent, an
inactive parent means the directory being decoded is being removed.
reconnect_one() then returns -ESTALE either way, because readdir
skips the removed child.

Hi Shakeel,

Shakeel Butt writes:

---

Not a big deal, but one thing changed from v3 that the changelog doesn't
mention. Without an ilookup() first, every caller now needs the
preallocated inode even when one is already hashed. Before this patch
iget_locked() returned a hashed inode without allocating. So when
new_inode() fails, decoding a handle for a live node whose inode is
cached now fails with -ENOMEM, and a stale handle gets -ENOMEM instead of
-ESTALE. kernfs_iop_lookup() does the same for a node that already has an
inode.

 From a quick check I did with failslab limited to inode_cache and an fd
held open on a cgroup2 directory, open_by_handle_at() on its handle
succeeds without this patch and fails with ENOMEM with it.

Now, new_inode() only fails there for an OOM victim, or in a memcg whose
OOM killer is disabled or has nothing left to kill, and those tasks are
failing most other allocations too, so I don't think it's worth
complicating kernfs_get_inode_locked() for. But it is a second case
besides an inactive node where an ilookup() first changes the result.

Not a problem, just an observation, so feel free to add:
