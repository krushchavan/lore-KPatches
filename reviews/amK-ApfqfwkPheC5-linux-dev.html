[PATCH v4 2/2] mm/vmscan: reduce lru_lock contention via vmstat-derived scan-balance cost

Submitted: 2026-07-24
Active on: 2026-07-24
Patch summary
This patch reduces lock contention in the Linux kernel's memory management system by introducing a new cost function for scan balancing, which is derived from vmstat metrics. The goal is to improve performance and reduce contention on the lru_lock. However, the exposure of two new metrics (pgrotate_anon and pgrotate_file) to userspace has raised questions about their usefulness and potential for confusion.

Johannes Weiner 2026-07-24 Inline Review Reviewed-by Needs Work LLM
The reviewer noted that the existing PGROTATED counter is not useful for understanding reclaim behavior, but the new counters proposed by the patch can be almost fully derived from existing counters. The reviewer suggested simplifying the counters and removing the noise caused by MADV_COLD driven deactivations.
Show original comment 
Hm, this is an interesting discussion.

The existing PGROTATED is kind of useless. When it's bumped:

- truncation fails and moves folios to the LRU tail for faster reclaim
- writeback ends on folio that was tried to reclaim, moves to LRU tail for fast retry

Ok, who needs to know this? The new counters you're adding, on the
other hand, they capture the information you frequently need for
understanding reclaim behavior.

That said, looking closer at this one more time, you can already
(almost) derive them fully from existing counters:

drotated = (dPGSCAN_ANON - dPGSTEAL_ANON) + dPGDEACTIVATE_ANON

The first two are already split by anon and file. The third you'd have
to (1) split by type and (2) stop counting, or have a separate event,
for MADV_COLD driven deactivations.

And (2) seems overdue anyway. There is no point in maintaining counts
for what userspace madvises. And it adds noise when it gets conflated
with a stat tracking kernel reclaim behavior.
