Patch summary
This patch addresses a long-standing issue in the FUSE (Filesystem in Userspace) implementation where fuse_ring creation is decoupled from entity registration, which can lead to incorrect behavior when using io-uring. The problem arises because the condition check in fuse_uring_cmd() uses an && operator instead of ||, allowing the use of io-uring even if the server hasn't sent the FUSE_OVER_IO_URING flag. This patch aims to fix this issue by properly enforcing the requirement for the FUSE_OVER_IO_URING flag when using io-uring.

The condition check in fuse_uring_cmd() is an && and not an ||. It
doesn't enforce that the server must have sent over FUSE_OVER_IO_URING
in the init reply to use fuse io-uring. With enable_uring=1 (which is
needed for the kernel to advertise FUSE_OVER_IO_URING in the init
request in the first place), the fuse io-uring logic proceeds
regardless of whether the server replied with the FUSE_OVER_IO_URING
flag or not.

Bernd Schubert 2026-08-19 Inline Review Reviewed-by Needs Work LLM
Bernd Schubert noted a lock order inversion issue in fuse_uring_cmd(), where the function takes queue->lock while holding fch->bg_lock, and also wants to take fch->bg_lock again, which can lead to a deadlock. He also pointed out that the wrong '&&' condition in fuse_uring_cmd() allows userspace to bypass the module option to enable io-uring by setting the flag directly.
