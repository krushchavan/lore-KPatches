Patch summary
This patch series addresses an issue where SDEI events can cause exceptions in the event handler, leading to unexpected behavior and crashes. The patches modify the SDEI event handling code to run the handler on kernel vectors instead of trampoline vectors, which are not suitable for synchronous exceptions. Additionally, the patches save and restore exception registers around the event handler to prevent overwriting of interrupted context's registers. This change improves the robustness of SDEI event handling and prevents issues such as CPU stalls, SIGILL, and SIGSEGV in user tasks.

The author acknowledged that the IRQ-like resume into user space must still go through the trampoline to map the kernel, and confirmed that the patch series addresses the issue of exceptions taken by the handler breaking the interrupted context.

From: "Kiryl Shutsemau (Meta)" <kas@kernel.org>

An SDEI event can land anywhere, and a synchronous exception taken by its
handler breaks the context it interrupted:

 - With KPTI, an event that lands in user space runs the handler on the
   trampoline vectors, whose current-EL half is empty. The exception
   loops there and the CPU is lost.

 - The exception overwrites ELR, SPSR, ESR and FAR. If the event landed
   in exception entry or return, the interrupted context runs on the
   handler's values: a task gets SIGILL, or the kernel oopses on a fault
   it never took.

Patch 1 runs the handler on the kernel vectors. Patch 2 saves and
restores the exception registers around it.

Handlers take such exceptions in normal operation now that SDEI delivers
NMI backtraces: show_regs() reads through _nofault() accessors that
fault, and a kprobe or WARN anywhere in the path takes a BRK.

Tested under QEMU TCG with TF-A, 4 CPUs, 20 x sysrq-l under load, with a
test-only copy_from_kernel_nofault() of address 0x10 in
sdei_nmi_handler():

 - v7.4-rc1, KPTI on: CPUs stuck in the trampoline vectors, RCU stalls.
 - v7.4-rc1, KPTI off: 60 "unsafe: exception during handler" warnings,
   SIGILL and SIGSEGV in user tasks, and an oops in execve().
 - With the series, KPTI on and off: no warnings, no stalls. The same
   with an eprobe on irq_disable that reads address 0x10, which faults
   inside irqentry_nmi_enter() when the event lands in user space.

An earlier revision of patch 2 was also run on arm64 hardware with
firmware SDEI, where a plain sysrq-l was enough to trigger the warning
without it.

Ada Diaz 2026-11-06 Inline Review Reviewed-by Needs Work LLM
Reviewer Ada Diaz noted that the patch does not handle the case where an exception is taken inside the event handler, which can lead to a lost CPU and incorrect exception handling. Reviewer Ada Diaz suggested that the issue is not with the SDEI handler but rather with arch/arm64/entry.S not properly handling SDEI events, and also pointed out that the SDEI trampoline may be missing some kernel entry logic which could break assumptions. Reviewer Ada Diaz suggested that SDEI exception handling should be unified with regular kernel entry by swapping VBAR in __sdei_asm_entry_trampoline and __sdei_asm_exit_trampoline, rather than doing special handling in the handler. Reviewer Ada Diaz suggested modifying do_sdei_event() to explicitly choose the correct vector base for KPTI=on, bypassing unmapped EL1 exceptions of the trampoline vector by using vectors instead of VBAR. Reviewer Ada Diaz suggested replacing the code in __sdei_handler() with changes from entry.S, without modifying the existing function. Reviewer Ada Diaz suggested making the vector base on return from firmware more explicit, citing consistency with other entry paths and potential for future de-duplication.
