[RFC PATCH] mm: bypass swap readahead for zswap

View on lore.kernel.org →
Submitted: 2026-07-07
Active on: 2026-07-07
Patch summary
This patch bypasses swap readahead for zswap, an in-memory compression backend similar to zram. The current implementation of swap readahead is optimized for traditional disk-based swap devices and can cause issues like inflated anon residency, page cache thrashing, and increased fault latency when applied to an in-memory backend. By skipping readahead for zswap, the patch aims to improve performance by reducing unnecessary prefetching of pages that are not needed. The results from testing this bypass show significant improvements in build time, swap-in/out rates, and reduced swap readahead hits.

Barry Song noted that bypassing swap readahead for zswap may not be necessary as the original patch description already mentioned that zswap is an in-memory backend and should not trigger swap readahead, but he did not provide any specific technical concerns or suggestions. Reviewer Barry Song expressed neutral sentiment towards the patch, stating that he is not opposed to either zram or zswap and acknowledging their importance in their respective domains. Reviewer Barry Song expressed concern that adding a bypass for swap readahead in zswap would require the readahead path to check whether folios are in zswap or not, which he finds potentially complex. Reviewer Barry Song noted that the approach could become complex and suggested either keeping the current patch or disabling readahead unconditionally when using zswap, without checking if the swap-in is coming from zswap. Reviewer Barry Song noted that bypassing swap readahead for zswap avoids an additional page fault, which is faster than handling two separate faults, but increases the complexity of do_swap_page(). Reviewer Barry Song noted that bypassing swap readahead for zswap only results in performance improvements when using small page-cluster sizes (1), but causes regressions for larger page-clusters (>2). He observed a bigger benefit for sequential swap-ins with larger page-clusters. Yes, because it avoids another page fault. Handling two pages in a
single page fault is faster than handling two separate page faults,
each faulting in one page. Since we've already read the data out
synchronously, we don't want to fault on it again. The downside is
that it increases the complexity of do_swap_page().

I'm not even trying to sell my approach—I did it just for fun.
do_swap_page() is already quite complex, and my fault-around
implementation only makes it more complicated. So I don't really want
to push for it to be merged upstream. I think it will become much more
attractive once we have hardware-assisted decompression in
do_swap_page(), where we no longer spend CPU cycles on
decompression.

---

Yep. I'm only seeing improvements with page-cluster=1, which uses a
small readahead window. For page-cluster > 2, I'm seeing performance
regressions on workloads such as kernel builds. On the other hand, a
larger page-cluster provides a bigger benefit for sequential swap-ins.
So it's not a universal win.
