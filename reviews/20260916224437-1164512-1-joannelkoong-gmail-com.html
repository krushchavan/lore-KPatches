[PATCH v2 0/3] mm: split underused anonymous mTHP folios

View on lore.kernel.org →
Submitted: 2026-09-25
Active on: 2026-09-28 • 2026-09-25
Patch summary
This patch series addresses memory regressions caused by enabling 2M THP=always on arm64 with 64k base pages. The patches split underused anonymous mTHP folios, which are not currently reclaimed under memory pressure. Patch 1 makes the thp_underused() function size-aware to accommodate larger folio sizes. Patch 2 optimizes existing behavior by keeping folios that can never be found underused off the deferred split queue. Patch 3 queues anonymous mTHP folios from map_anon_folio_pte_nopf(), mirroring what is already done for PMD folios. The patches aim to provide a solution for deploying 2M THP=always on arm64 without causing memory regressions.
Joanne Koong (author) 2026-09-25 Neutral LLM
The author is addressing David's concern about the scaling of khugepaged_max_ptes_none, which affects both PMD THP and mTHP folios. The author acknowledges that David was primarily arguing against adding overhead for most Linux installations, but agrees to add David's Suggested-by: tag in v3. The author also ran a benchmark to measure contention on the deferred split list lock, finding that it comes from the free path rather than enqueuing, and is considering moving the unqueue out of the loop where the lruvec lock is held.

I ran Barry's microbenchmark to get a sense of the contention (more of
the details are in my previous reply to Barry [1]). With max_ptes_none
set to 0 so that everything gets queued, and toggling shrink_underused
0 vs 1 with patch 3 applied, I saw roughly a 15.8% and 11.5%
performance hit on runtime at 16k and 32k, but only 1.1% at 64k and
noisy above that.

I didn't see the cost being from contention on the deferred list's
lock though. Perf showed that it was coming from
folio_lruvec_lock_irqsave, and I think that's from the free path where
in folios_put_refs(), __page_cache_release() keeps the lruvec locked
across the whole batch, and folio_unqueue_deferred_split() gets called
from inside that loop with that lruvec lock held. I don't think
batching the enqueues would help in that case, since the cost is
coming from the unqueue side and on a path that's already batched. I
think maybe we could move the unqueue out where the lruvec lock
doesn't need to be held while the unqueueing happens, but I need to
look more into that.

Based off the benchmark results in [1] and [2], I think the cutoff
needs to be at 64k where we exclude anything under that. On 4k base
pages, this is order 4, but on 64k base pages, order 4 would mean 1M,
which I think would be overly conservative. I think it makes more
sense to express it as an absolute threshold value instead of by
order. I'll try to find an arm64 machine to double-check this on.
