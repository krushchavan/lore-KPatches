Patch summary
This patch series addresses a long-standing issue in the Btrfs file system where memory allocation failures can cause the file system to abort. The patches rework the code to perform memory allocations before critical points, preventing aborts due to ENOMEM errors. This includes changes to directory morphing and orphan handling, with additional tests added to exercise the new behavior. While not all potential cases are covered, this series is designed to work in conjunction with other patches to address remaining issues.

Qu Wenruo 2026-08-06 Inline Review Reviewed-by Needs Work LLM
Reviewer Qu Wenruo noted that only two callsites use on-stack memory for the prealloc structure and suggested converting to a heap-based solution. Additionally, they pointed out a potential issue with the lifespan management of btrfs_dir_index_prealloc, suggesting a more straightforward approach using regular heap memory allocation.
Show original comment 
In the end, there are only two callsites using on-stack memory for 
prealloc structure, one in btrfs_rename() and one in 
btrfs_insert_dir_item().

So it would be not that hard to convert to heap memory based solution.


One thing I found a little weird is related to the lifespan management 
of btrfs_dir_index_prealloc.

We have several call sites doing things like:

	struct btrfs_dir_index_prealloc prealloc = { };

	ret = btrfs_prealloc_delayed_dir_index();

	ret = btrfs_add_link(..., prealloc.item ? prealloc : NULL);
	prealloc.item = NULL;

Which looks a little weird to me, as we're using item to indicate if the 
structure is properly allocated, not the structure itself.

If we go regular heap memory allocation, it would be more 
straightforward and more common:

	struct btrfs_dir_index_prealloc *prealloc = NULL;

	prealloc = btrfs_prealloc_delayed_dir_index();

	ret = btrfs_add_link(..., prealloc);
	prealloc = NULL;

Feel free to ignore this one, it's mostly preference.

Thanks,
Qu
