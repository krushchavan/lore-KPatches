Patch summary
This patch improves the handling of swap cache folios by dropping them from their cache once writeback completes, rather than leaving them for reclaim to find later. This is achieved by adding a new function `swap_writeback_dropbehind_folio` that takes a folio as an argument and drops it from its cache after writeback has completed. The patch also updates several other functions to use this new function. The goal of the patch is to improve performance by reducing the number of times swap cache folios are scanned for reclaim, which can be expensive operations.
Alexandre Ghiti 2026-08-24 Inline Review Reviewed-by Neutral LLM
Reviewer noted that Tal's patchset defers atomic context to a workqueue, causing dropbehind folios on synchronous devices to be freed inline, which is not possible due to the zswap reference held by the writeback path. The reviewer suggested dropping the zswap reference before __swap_writepage() to fix the issue.

As you noted, in my implementation, a race was possible between the
worker and the folio_put() in zswap_writeback_entry(). Now with Tal's
patchset which *only* defers atomic context to a workqueue, the
dropbehind folios on synchronous devices get freed inline which is not
possible because of the reference held by the zswap writeback path.

But it's cleanly fixable by dropping the zswap reference before
__swap_writepage(): the folio is locked (when it is allocated) until
writeback starts, then PG_writeback prevents the folio removal from
the swapcache and right before clearing PG_writeback in
folio_end_writeback_no_dropbehind(), folio_end_writeback() takes a
reference! So remove_mapping() is happy with the refcount :)

So there are no more races as you pointed out, since we drop the
reference before the writeback. I'll post the v4 today.

Thanks again for your comment.

Alex
