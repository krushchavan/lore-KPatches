Patch summary
This patch bypasses swap readahead for zswap, an in-memory synchronous backend similar to zram. The current implementation of swap readahead can lead to pointless prefetching of pages, causing increased anon residency and page cache thrashing. By bypassing readahead for zswap, the patch aims to reduce this overhead and improve performance. Measurements show significant gains in build time, zswap-in/out rates, and reduced swap readahead hits. The patch reuses existing code and adds a new helper function to check if a swap entry is synchronous.

Barry Song 2026-10-12 Reviewed-by Needs Work LLM
Reviewer Barry Song noted that if a high-hit-rate readahead algorithm is developed, it may be necessary to map all readahead folios at the same time in do_swap_page() to avoid increasing total work for synchronous I/O.
Show original comment 
In that case, if we can develop an accurate readahead algorithm with a
high hit rate for readahead folios, we will probably also need to map
them at the same time, as proposed in [1]. For example, if we readahead
4 folios, we should map them all together in `do_swap_page()`.
Otherwise, the cost of future minor faults can still be comparable to
the decompression cost. Readahead alone would therefore increase the
total work, which can be quite significant for synchronous I/O.

[1] https://lore.kernel.org/linux-mm/CAGsJ_4xM=WnFO-OuwVude-DQ_UkaCi_zF_bXBP9Li5+ZPNy0VQ@mail.gmail.com/

Barry Song 2026-10-12 Needs Work LLM
Reviewer Barry Song noted that asynchronous wake-up latency is highly unpredictable and can be much longer than the time it takes to complete mapping and decompression work in do_swap_page(), which makes async zram readahead unreliable without hardware queues.
Show original comment 
I am quite sure I tried this 3 or 4 months ago, and the
performance was very poor. The problem is that async wake-up
latency is highly unpredictable. For example, do_swap_page()
can complete all the mapping and decompression work in less
than 10 us. However, if we queue the work to an async thread,
its wake-up latency alone could be much longer than 10 us.

Based on my results, async zram readahead only works if we have
hardware queues rather than relying on async threads.
