[PATCH for-7.5 0/5] memcg: clean up memory.high enforcement

Active on: 2026-10-14 • 2026-10-12
Patch summary
This patch series cleans up the enforcement of memory.high limits in Linux by moving it to a separate function and using a worker for kernel threads and remote charges. The changes aim to improve performance by avoiding unnecessary reclaiming and sleeping during charges, and also fix issues with high handler usage. The patches modify the memcg_enforce_high() function, add handling for kernel threads and remote charges, introduce a guard against queuing work from PF_MEMALLOC tasks, and simplify the scan and comments.
Harry Yoo 2026-10-12 Reviewed-by Needs Work LLM
Reviewer Harry Yoo noted that try_charge_memcg() is doing too much and suggested breaking out the memory.high enforcement into a new function, memcg_enforce_high(), to improve readability and maintainability.

The force charge (and ENOMEM) paths bypass the memory.high enforcement
altogether. Only successful charges (done_restock label) goes through
memory.high enforcement. So, even if we move this check in try_charge_memcg, it
will still be a separate check before calling high enforcement function. I think
this check is very high_work specific and better to be in the high enforcement
function.

On Sat 10-10-26 14:09:54, Shakeel Butt wrote:
> Kernel threads never return to userspace, so deferred memory.high
> reclaim does not run. Reclaim and throttling during a charge can also
> delay work they do for other tasks.
> 
> Treat kernel threads like interrupts. Queue high_work for the first
> cgroup over memory.high and skip reclaim and throttling in the charging
> thread.
> 
> User workers created by create_io_thread() and vhost_task_create() keep
> their current behavior. Vhost kernel threads use the new path, even when
> they borrow the owner's mm.
> 
> The worker requests a fixed batch of pages each time. A fast allocator
> can keep usage well above memory.high. Kernel threads also skip
> memory.swap.high throttling and its high-event reporting. The memory.max
> and memory.swap.max checks stay the same.
> 
> Suggested-by: Tejun Heo <tj@kernel.org>
> Signed-off-by: Shakeel Butt <shakeel.butt@linux.dev>

yes this makes sense as a general improvemnt.
