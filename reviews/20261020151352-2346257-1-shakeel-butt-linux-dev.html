[RFC PATCH] x86,resctrl: Read event counters with an IPI when the read cannot block

View on lore.kernel.org →
Submitted: 2026-10-21  ·  Last comment: 2026-10-22
Active on: 2026-10-22 • 2026-10-21
Patch summary
This patch introduces a new configuration option CONFIG_RESCTRL_MON_READ_IRQSAFE to allow reading event counters with interrupts off on the current CPU or using an IPI when necessary. This is done to reduce long stalls caused by readers sleeping while holding rdtgroup_mutex, which can lead to gaps in monitoring data. The patch adds support for x86 architecture and provides results showing a significant reduction in hold time per read and time off CPU while holding the mutex.
Reinette Chatre 2026-10-21 Inline Review Reviewed-by Needs Work LLM
Reviewer Reinette Chatre pointed out that the patch does not handle the case where CONFIG_RESCTRL_MON_READ_IRQSAFE is disabled, which would cause a regression on architectures other than x86. Reviewer noted that the patch's solution for high-performance monitoring is overly aggressive, given the existing limitations of the resctrl mon_data files interface. Reviewer Reinette Chatre asked Shakeel Butt to consider the thread that followed his previous proposal, implying that there may be relevant information or context that was not addressed in the current patch. Reviewer Reinette Chatre noted that the proposed patch only slightly adjusts the limit of how many monitor groups this deployment can support, and suggested considering a per-group rate as proposed by Peter Newman to enable full capability of the systems. Reviewer noted that reading 128 MON groups with interrupts off can take up to 131 us, which may be significant for applications where the kernel is also monitoring itself. Reviewer questioned the necessity of reading event counters every 100 ms, suggesting that the overflow handler's one-second interval is sufficient for querying data Reviewer noted that the patch does not fully address the scalability issue for large numbers of monitoring groups, and suggested considering per-group rate files as a potential solution. Reviewer Reinette Chatre suggested avoiding a config option and instead making read_irq_safe a per-resource property, citing concerns about the scope of change as multiple architectural drivers are involved. Reviewer noted that the patch's use of raw_ functions to disable preemption is only effective when preemption is disabled, and suggested it may be a re-implementation of smp_call_function_any() Reviewer Reinette Chatre noted that the '!tick_nohz_full_cpu(this_cpu)' check in the patch defeats its own goal of preventing an IPI when a reader is pinned to the domain, and suggested reordering the logic to prefer the current CPU whenever it's in the domain, nohz_full or not.

Peter Newman 2026-10-22 Reviewed-by Needs Work LLM
Reviewer Peter Newman noted that the patch does not handle the case where the target CPU is in a nohz_full domain, and requested that an IPI be sent to wake up the kworker on the target CPU. Reviewer Peter Newman expressed concerns about the practicality of implementing the patch, citing existing issues with MBM implementations on AMD and a preference to use the offcore PMU instead. Reviewer pointed out that interrupt masking has a limited impact on latency since interrupts are reenabled between counter reads, and instead highlighted the issue of workload scheduling being impacted by this feature, suggesting it would need to be disabled in nohz_full mode for high-availability products.
