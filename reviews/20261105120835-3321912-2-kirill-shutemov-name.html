[PATCH v2 1/2] arm64: sdei: Run the event handler on the kernel vectors

View on lore.kernel.org →
Submitted: 2026-11-05
Active on: 2026-11-05
Patch summary
This patch fixes an issue where SDEI events dispatched to the kernel vectors in user space cause a CPU hang due to undefined instruction exceptions. The patch installs the kernel vectors in the __sdei_handler function when VBAR_EL1 holds trampoline vectors, and restores it before returning to firmware. This ensures that exceptions taken by the handler execute correctly and do not loop forever. Additionally, this change covers irqentry_nmi_enter() and irqentry_nmi_exit(), which can also take an exception. The patch addresses a problem where SDEI events dispatched in user space cause CPU hangs due to undefined instruction exceptions.
Kiryl Shutsemau (author) 2026-11-05 Neutral LLM
The author acknowledged that the current implementation of __sdei_handler() does not handle the case where VBAR_EL1 holds the trampoline vectors, and explained how they plan to fix this by switching to the kernel vectors when necessary.

From: "Kiryl Shutsemau (Meta)" <kas@kernel.org>

With KPTI, VBAR_EL1 holds the trampoline vectors from the return to EL0
until the next exception from EL0 maps the kernel and installs the
kernel vectors. The trampoline vectors only handle exceptions from EL0;
their current-EL half is zero-filled.

An SDEI event is dispatched regardless of PSTATE.DAIF, so it lands there
whenever the CPU is in user space. The SDEI entry trampoline maps the
kernel but leaves VBAR_EL1 alone. An exception taken by the handler then
executes the zeros, takes an undefined instruction exception to the same
vector, and loops there forever. The event never completes and the CPU
is lost; RCU stall reports are the first sign of it.

RAS notifications land in user space whenever a task consumes the
error, and NMI backtraces land wherever the CPU happens to be. The GHES
handler takes no exception on its own, but any exception in the handler
path does it: a WARN, a kprobe hit, or a fault fixed up by a _nofault()
accessor.

Install the kernel vectors in __sdei_handler() when VBAR_EL1 holds the
trampoline vectors, and restore it before returning to firmware. The
switch covers irqentry_nmi_enter() and irqentry_nmi_exit() too, as Usama
Arif pointed out: their tracepoints and context tracking WARNs can take
an exception as well.

The IRQ-like resume into user space must still go through the
trampoline to map the kernel. do_sdei_event() takes the interrupted
VBAR_EL1 and keeps basing the resume address on it.

Sashiko had a comment that the above should be raw_cpu_read() since with
preempt debugging and pseudo-NMIs, irqs_disabled() is false here and the
check in __this_cpu_read() will warn.

Thinking about it, further down on the irqentry_nmi_enter() ->
lockdep_hardirqs_off() we'll hit the irqs_disabled() issue again. We
could just do a raw_local_irq_save/restore() around this function.
Unnecessary for DAIF but useful with pseudo-NMIs.

Alternatively, __sdei_asm_handler() could save/restore PMR and change
the priorities similar to the kernel_entry code. Actually, this may be
better since do_sdei_event() also checks regs_irqs_disabled() and we
don't have any regs->pmr populated.

Worth a separate patch to fix SDEI handling with pseudo-NMI on and no
changes to __this_cpu_read() above needed. So, for this patch:
