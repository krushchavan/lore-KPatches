[PATCH 0/2] firmware: arm_sdei: Fix NMI backtrace lockups on idle CPUs

Patch summary
This patch series fixes a lockup issue on idle CPUs caused by SDEI NMI backtraces. The problem occurs when an event is signaled to all CPUs, including those in a power-down state where SDEI is masked. To fix this, the patches prevent event 0 from being sent to masked PEs and send regular backtrace IPIs to these CPUs instead. This approach ensures that the system remains responsive even during idle states.

The SDEI NMI backtrace signals event 0 to every other CPU, including the
ones in a power-down idle state, where the kernel has SDEI masked. TF-A
acknowledges the SGI behind event 0 on a masked PE and never ends it,
and the PE takes no Non-secure interrupt again. Jinjie hit it on a
384-CPU HIP12, where one sysrq-l locked up the machine.

Patch 1 keeps event 0 away from masked PEs. Patch 2 sends the regular
backtrace IPI to the CPUs that SDEI refused, which wakes them.

TF-A v2.13 and later refuse to signal a masked PE, but a PE that masks
right after the check still takes the SGI. The TF-A fix is under review:

  https://review.trustedfirmware.org/c/TF-A/trusted-firmware-a/+/55414

Tested under QEMU TCG with TF-A built without that check, 4 CPUs. One
CPU masks and unmasks SDEI in a loop, through cpu_pm, the mask calls and
CPU hotplug, while another signals it; sysrq-l afterwards. Signalling
with plain SMCs, as the kernel does now, wedges the target. With the
series every run passed, lockdep included, and a panic in the middle of
it completes.

Jinjie ran an earlier version on HIP12 with the power-down state
enabled: sysrq-l got 384/384 answers every run. The handshake has
changed since; Jinjie, could you give this one a run as well?

Kiryl (Meta) (author) 2026-11-25 Neutral LLM
The author addressed YinFengwei's concern that the patch may cause a deadlock when another CPU holds the sdei_lock at the end of smp_send_stop(). The author explained that if another CPU is stopped in the middle of signalling, it will never drop the lock, but if nobody holds the lock, there is nothing for it to keep out. The author stated that telling the two apart takes a trylock and on failure, they would go ahead without the lock anyway. The author is addressing a concern about the potential for a race condition when reading and writing to the pe->unmasked flag, specifically in the context of the notifier running with IRQs off. The author explains that no store can race with this load due to the IRQs being off, but acknowledges that other types of interrupts (stop or panic from an SDEI event or pseudo-NMI) could still interrupt it. No fix is planned.

If another CPU holds it at this point, that CPU was stopped in the
middle of signalling this one, and it will never drop the lock. The

If nobody holds it, there is nothing for it to keep out. This runs at

sender stopped after it took the lock has either counted its signal,

Telling the two apart takes a trylock, and on failure we would go ahead

No.

We read the flag of this CPU, and only this CPU writes pe->unmasked.
The notifier runs with IRQs off, so no store can race with this load.

What can still interrupt it, a stop or a panic from an SDEI event or a
pseudo-NMI, does not return here.

READ_ONCE()/WRITE_ONCE() are for sdei_event_signal(), which reads the
flag from another CPU.

Left plain, KCSAN will report it if that ever changes. See item 5 under
"Use of Plain C-Language Accesses" in
