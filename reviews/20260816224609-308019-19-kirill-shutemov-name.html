Patch summary
This patch adds functionality to install the destinations at PTE level in the mm/collapse code. It includes a verify step to ensure that the window is still the round's to publish, and an abort step to undo a frozen candidate that cannot be published. The patch also handles publishing, which involves updating the destination's rmap and LRU insertion before its PTEs are updated. Additionally, it adds a terminal layer for PMD-order candidates and includes code to handle zapped slots and racing MADV_DONTNEED operations.
Lance Yang 2026-08-25 Inline Review Reviewed-by Neutral LLM
Lance Yang noted that KSM zero-page accounting gets out of sync when a saved zero PTE is restored in the collapse_abort_candidate() function, as it does not drop the counters if the PTE was previously marked dirty by ksm_map_zero_page(). He suggested adding a new function collapse_unmap_zero_pages() to handle this case and proposed modifying the collapse_install_pmd() and collapse_install() functions to call this new function.

Well ... KSM zero-page accounting gets out of sync here.

Say a saved zero PTE came from KSM. ksm_map_zero_page() has already
bumped global + per-mm counters. ksm_might_unmap_zero_page() uses its|
dirty bit to drop them again later:

#define is_ksm_zero_pte(pte)	(is_zero_pfn(pte_pfn(pte)) && pte_dirty(pte))

static inline void ksm_map_zero_page(struct mm_struct *mm)
{
	atomic_long_inc(&ksm_zero_pages);
	atomic_long_inc(&mm->ksm_zero_pages);
}

static inline void ksm_might_unmap_zero_page(struct mm_struct *mm, pte_t pte)
{
	if (is_ksm_zero_pte(pte)) {
		atomic_long_dec(&ksm_zero_pages);
		atomic_long_dec(&mm->ksm_zero_pages);
	}
}

Right, once a candidate reaches install, those counters stay valid only
if collapse_abort_candidate() restores the saved PTE. A successful PTE
install doesn't restore it. Neither does an abort after the slot was
refilled or the PTE table disappeared. Patch #19 has the same
successful-install case in collapse_install_pmd() ...

I was thinking of something like this:
