Patch summary
This patch series introduces a fast path for __access_remote_vm that uses per-VMA locks instead of the process-wide mmap_lock, improving system monitoring reliability and speeding up the function under contention. The fast path is only enabled when it's safe to do so, requiring a kernel with per-VMA locks, RCU page table freeing, and specific VMA types excluded. This change aims to address issues where processes get stuck holding the mmap_lock for extended periods, hindering system monitoring tools' ability to assess and log situations.

Author addressed David's concern that normal pages could be accessed using only per-VMA locks, proposing to implement a locking function for __access_remote_vm() that takes the appropriate lock and handles expand_stack() calls. Author is addressing David's (Arm) feedback on whether __access_remote_vm can use gup-fast for accesses entirely within a single VMA, and considering switching to gup-fast as an alternative to eliding the first VMA lookup in get_user_pages. So:

pte_t *pte_offset_map_lock(struct mm_struct *mm, pmd_t *pmd,
			   unsigned long addr, spinlock_t **ptlp)
{
	spinlock_t *ptl;
	pmd_t pmdval;
	pte_t *pte;
again:
	pte = __pte_offset_map(pmd, addr, &pmdval);
	if (unlikely(!pte))
		return pte;
	ptl = pte_lockptr(mm, &pmdval);
	spin_lock(ptl);
	if (likely(pmd_same(pmdval, pmdp_get_lockless(pmd)))) {
		*ptlp = ptl;
		return pte;
	}
	pte_unmap_unlock(pte, ptl);
	goto again;
}

__pte_offset_map() takes the RCU lock, then locklessly retrieves a pointer
to the PTE page table.

As mentioned above, khugepaged retraction causing PTE page table freeing is
also under RCU, so this is safe:

	retract_page_tables() -> pte_free_defer() -> RCU
	try_collapse_pte_mapped_thp() -> pte_free_defer() -> RCU

And on page table retraction, importantly, the PMD entry is cleared _with
the PTE PTL held_, e.g. in retract_page_tables():

		ptl = pte_lockptr(mm, pmd);
		if (ptl != pml)
			spin_lock_nested(ptl, SINGLE_DEPTH_NESTING);
		...
		if (likely(file_backed_vma_is_retractable(vma))) {
			pgt_pmd = pmdp_collapse_flush(vma, addr, pmd);
			...
		}

		if (ptl != pml)
			spin_unlock(ptl);

For anon, we take the mmap write lock/VMA write lock anyway.

And going back to pte_offset_map_lock() - we _recheck the PMD under the
PTL_.

So if the PMD was since cleared, we don't get anything stale. If it wasn't,
then we hold the PTE PTL and exclude khugepaged from changing things under
us.

Thus folio_walk_start(), which holds the PTE PTL, is perfectly fine, and
folio_walk_end() marks the point at which things are no longer safe (but
then we're done with the folio).

So again I don't think there's any problem here, actually.
