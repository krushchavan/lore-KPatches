Patch summary
This patch series removes the 'pipe buffer stealing' feature, which allows a consumer of a pipe to take its page instead of copying the data. The feature was used by fuse and virtio_console, but it has caused issues and required multiple fixes. The patch replaces this behavior with a copy operation when stealing fails, and removes the related code. This change is expected to improve the stability and maintainability of the kernel.

Christian Brauner 2026-11-11 Inline Review Reviewed-by Needs Work LLM
Christian Brauner noted that the patch to remove pipe buffer stealing does not address a potential issue where a pipe buffer can span multiple pages of a compound page, which was previously fixed by mapping one subpage at a time in copy_page_to_iter(). He suggested applying the same fix here.
Show original comment 
So the fix below is what we've done before for pipes and I think it's
the right thing to do here too. I put the following on vfs.fixes:

-- >8 --
From: Christian Brauner <brauner@kernel.org>
Subject: [PATCH] virtio_console: copy pipe buffers that span multiple pages

pipe_to_sg() maps buf->page with kmap_local_page() and then copies up
to a page worth of data starting at buf->offset. But kmap_local_page()
only maps a single page and a pipe buffer can span multiple pages of a
compound page with buf->offset pointing past the first one:

- skb_splice_bits() for AF_UNIX and TCP sockets
- tracing_buffers_splice_read() with sub-buffers larger than a page
- fuse_dev_splice_read() which hands out the page cache folios of WRITE
  requests. Those can be large folios since b46e09667411 ("fuse: enable
  large folios").

Without HIGHMEM this happens to work because kmap_local_page() is just
page_address() and a compound page is contiguous in the direct map.
With HIGHMEM the copy reads past the mapping. A fuse server on a 32-bit
HIGHMEM guest that splices a WRITE request into a virtio port crashes:

  BUG: unable to handle page fault for address: fffab000
  #PF: supervisor read access in kernel mode
  #PF: error_code(0x0000) - not-present page
  Oops: Oops: 0000 [#1] SMP
  EIP: pipe_to_sg+0x158/0x1e0
  Call Trace:
   __splice_from_pipe+0xd6/0x1f0
   port_fops_splice_write+0xf9/0x170
   do_splice+0x2c1/0x810
   __ia32_sys_splice+0x2e7/0x310
   ia32_sys_call+0x1916/0x2510
   __do_fast_syscall_32+0xd4/0x550
   do_fast_syscall_32+0x32/0x70
   do_SYSENTER_32+0x15/0x20
   entry_SYSENTER_32+0xa6/0x115

pipe_read() had the same problem and 08aa64796016 ("teach
copy_page_to_iter() to handle compound pages") fixed it by mapping one
subpage at a time. So copy the buffer with copy_page_to_iter() as well.

Fixes: b46e09667411 ("fuse: enable large folios")

I tried to push for what I thought was an aggressive timeline
last year, but that would still keep the Arm bits for a couple more
LTS releases and only gradually reduce the scope of highmem in the
meantime, removing support from architectures, file systems, and
drivers where possible. See https://lwn.net/Articles/1051010/
for a summary of my talk in Tokyo, including the slides and
a link to the video for anyone wanting more details.

I also prepared a number of patches towards this, but have so
far not been great at following up to get them merged, sorry
about that.
I definitely still want to revisit this soon, in particular the
bits about defaulting to VMSPLIT_2G_OPT, and probably my patch
to allow having (limited) discontiguous lowmem on Arm systems
with a large MMIO hole.

Scope-wise I think we absolutely need zsmalloc (zram/zswap)
on arm32 to work with GFP_HIGHUSER, but enough people have told me
that they still expect to need anonymous memory and ext4 page
cache for a while, and probably powerpc32. The majority
of __GFP_HIGHMEM allocations can probably just be converted
to use lowmem, which would eliminate a good chunk of kmap()
calls as well. In my attempts to do that, I came across two
problems I'd have to solve though:

 - Movable allocations (GFP_HIGHUSER_MOVABLE) imply highmem.
   while I think only 64-bit architectures support movable
   pages today, we cannot currently express an allocation
   that should be movable on 64-bit but lowmem on 32-bit.

 - Internal users of tmpfs (in particular DRM/GEM) usually
   don't want highmem or movable pages, but actual tmpfs
   does default to GFP_HIGHUSER_MOVABLE. Separating the two
   is complicated.

I added a few people to Cc here that I believe care about
having several more LTS releases with some highmem support
because of existing customer requirements.

     Arnd
