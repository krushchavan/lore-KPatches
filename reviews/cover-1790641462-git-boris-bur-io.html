Patch summary
The patch series aims to improve the performance of the Btrfs allocator, but several reviewers have raised concerns about scalability and potential issues with replacing the current locking mechanism.
Boris Burkov 2026-09-29 Neutral LLM
Raised scalability concerns about replacing the current locking mechanism with a percpu semaphore or RCU list, suggesting that different arenas like memory allocators might be necessary to address performance issues.
Signals: scalability concerns
Martin Raiber 2026-09-29 Neutral LLM
Expressed skepticism about replacing the current locking mechanism with a percpu semaphore, suggesting that it might not be sufficient to address performance issues and proposing alternative approaches like RCU lists or different arenas.

> I considered this while working on the size class stuff some years ago.
> If you look into the free space cache inside each block group, it does
> in fact index by gap size as well as gap offset.
>
> However if you do that at the block group level, then each allocation
> requires a write to the global ordering of block groups so that means
> having many parallel allocating threads now requires them to fight over
> a write lock on that ordered structure. I think that at least rules out
> naive solutions.
>
> You could probably resolve it with some more clever scheme like batching
> or queuing the work to update the ordering, or maybe some duplicated
> view with atomic cut overs.
>
> If you are interested in allocator performance, another thing we should
> consider is resurrecting more of
