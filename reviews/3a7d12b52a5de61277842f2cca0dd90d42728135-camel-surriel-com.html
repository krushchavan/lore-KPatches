[PATCH 1/8] mm/gup: break out gup_fill_pages() helper

View on lore.kernel.org →
Submitted: 2026-11-03
Active on: 2026-11-03
Patch summary
This patch breaks out a new helper function from gup_fill_pages() to simplify code and improve maintainability. The current implementation has inconsistent behavior, as some callers check for page existence while others do not. By moving the cache flushes to __get_user_pages(), the patch aims to reduce complexity and potentially merge more helper functions between slow GUP and fast GUP.
Rik Riel (author) 2026-11-03 Needs Work LLM
Author acknowledged that the patch by itself isn't super useful but agreed to restructure it in a future version (v2) to split out array filling from cache flushing and move cache flushing under its own helper, allowing GUP-fast and regular GUP to share the same helper. Author addressed David's concern about the callers of gup_fill_pages() needing a cache flush by listing specific callers and proposing to move the flushing to get_user_pages_remote() and pin_user_pages_remote(). The author asks for feedback on whether to fold this into the existing series or send it as a separate prequel series.

It looks like 2 of the 3 callers of gup_fill_pages()
check for pages existing. The other does not.

Should we just have the check in this one place, and

---

I think we could, but it does not look like any of
them need it.

Out of the 83 callers of gup_fast, many DMA into the
page, and the drivers do their own flushing. Also,
flushing before the DMA write doesn't help.

KVM, Infiniband, and others pin the pages, sometimes
for longer periods of time, and either flush around 
their reads and writes, or run only on architectures
where we don't need to.

The others access the page through the user's own
virtual address, which again does not require a
dcache flush.

Only a small number of slow GUP callers need dcache
flushes.

It may make more sense to move the cache flushes
all the way out into __get_user_pages() and away
from the follow_page_mask() call chain, so we can
maybe merge more of the helper functions between
slow GUP and fast GUP.

---

I think all of those could use the same helper
function I am breaking out here, once the dcache
flushing moves to its own helper.
