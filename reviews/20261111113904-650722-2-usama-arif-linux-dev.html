[PATCH 1/3] mm: don't PTE-batch a swap-in over a hardware-poisoned subpage

View on lore.kernel.org →
Submitted: 2026-11-11  ·  Last comment: 2026-11-12
Active on: 2026-11-12 • 2026-11-11
Patch summary
This patch prevents the Linux kernel from batching swap-in operations over a hardware-poisoned subpage. The existing check for PageHWPoison() only looks at the faulting page, but the large-folio batching path maps the rest of the folio without checking other subpages. This can lead to a poisoned subpage being mapped and not triggering a fault. To fix this, the patch adds a new function folio_has_any_hwpoisoned_page() that scans all subpages for HWPoison(), and uses it in do_swap_page() to skip batching when a poisoned subpage is found.
Usama Arif (author) 2026-11-11 Neutral LLM
Author acknowledged that the swapoff path needs to drop the per-vswap spinlock before calling try_to_unmap(), agreed to restructure in v2, but did not provide a clear indication of whether this change will be made in the current patch series or a future one. Author acknowledged that swapping in requires checking every subpage and accepted the trade-off of added cost for correctness. The author addressed Lorenzo's concern about PG_has_hwpoisoned being set after a THP split, explaining that it only gets set once the folio reference is held and get_hwpoison_page() gives up if it can't get a reference. However, they acknowledged that this doesn't cover the case of a large folio briefly off the LRU, which can still be mapped afterwards. The author addressed Lorenzo's concern that memory_failure() can leave a folio flag clear, allowing a poisoned subpage to be mapped without being faulted. The author explained the issue occurs when get_hwpoison_page() fails for a folio off the LRU and noted that memory_failure() should split the folio and isolate the bad page in such cases. They also suggested adding an additional check for anon folios before checking for HWPoison.

Hello Lorenzo,

Thanks for the reviews!

---

Swapping in requires checking every subpage, so there would be a cost.
I guess trading it off for correctness :(

---

PG_has_hwpoisoned lives in the second page, so memory_failure() only
sets it once it holds a folio reference, otherwise it could race with a
THP split. If get_hwpoison_page() can't get a reference,
memory_failure() gives up with only the subpage marked. The comment
above folio_set_has_hwpoisoned() in memory_failure() says that is fine:

  Don't need care about the above error handling paths for
  get_hwpoison_page() since they handle either free page
  or unhandlable page.

But a large folio that is briefly off the LRU, e.g. isolated by
reclaim, takes those paths too and can still be mapped afterwards.

---

The error hits a folio that is already in the swap
cache, e.g. while reclaim has it off the LRU to write it out, and
get_hwpoison_page() fails for any folio that is off the LRU. Normally
memory_failure() would split the folio and isolate the bad page (for
an uncorrected error there is nothing to migrate; that is soft
offline). Here it does neither, and the folio stays in the swap cache
with only the subpage marked.

While looking at this I also noticed that the fallback drops a freshly
read (not yet anon) folio from the swap cache and frees it with the
poisoned page in it. We should actually actually also check folio_test_anon()
before checking folio_has_any_hwpoisoned_page().
